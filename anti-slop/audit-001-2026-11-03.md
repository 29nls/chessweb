# Anti-Slop Audit 001: ChessWeb

- **Date:** 2026-11-03
- **Mode:** AFTER (explicit session override)
- **Scope:** full frontend UI/UX, all six routes
- **Rulebook:** `antislop.md` (R-01 to R-40, three tiers) + `skills/antislop-ui/SKILL.md`
- **Direction source:** `DESIGN.md` (present, read as data)
- **Source modified:** none. This is a read-only audit.

Reading this as: a chess study and play workspace for casual and competitive players, in an editorial scoresheet-and-graphite visual language, dial **ENERGY 2 / RHYTHM 2 / MOTION 1**.

---

## 1. Method and evidence standard

Findings are backed by three kinds of evidence, and each finding states which it uses:

1. **Measured in a running build.** The production bundle was served on `localhost:3000` and inspected in Chromium at 360, 390, 768, 1024, and 1440px, in both themes. Layout rects, computed styles, and contrast ratios were read from the live DOM.
2. **Source citation.** Exact file and line numbers.
3. **Screenshots** in `anti-slop/evidence/`.

Contrast ratios were computed with the WCAG relative-luminance formula against the nearest opaque ancestor background. Where a value is a gradient, the worst stop is reported. Nothing in this report is an estimate presented as a measurement.

**Honest limitation:** this build was served statically with no Supabase credentials, so `/online` rendered its lobby and `/history` rendered its error state. The signed-in, mid-game, and populated-history states were **not** visually inspected. Findings on those states come from source inspection only and are marked as such.

---

## 2. Executive summary

The design system is better than the average generated app. There is a real `DESIGN.md`, real tokens, a coherent editorial voice, a working light/dark toggle, and thorough `prefers-reduced-motion` handling. The base palette is deliberate and does not look like default AI output.

The problem is **accretion, not absence of direction**. Three generations of styling are layered on top of each other and were never reconciled:

- `index.css` defines a complete blue/slate token set on `:root`.
- `design-system.css` defines a second, different copper/sage token set on `:root`, and wins by import order.
- Individual page stylesheets still hardcode the older blue, emerald, and violet hex values, bypassing the tokens entirely.

The visible consequences are a primary button whose background is a blue-to-emerald gradient while its text is near-black, six landing badges in four off-palette hues that all fail contrast, and a puzzle page whose three-column grid never applies because the CSS selector expects an ancestor that does not exist.

**Counts:** 30 findings, 10 HIGH, 13 MEDIUM, 7 LOW.

**The three that matter most:**

- **F-006 / F-007**: the primary button and all landing badges fail WCAG AA contrast. These are Hard Gate failures affecting the two most-clicked elements in the app.
- **F-001**: the puzzle and puzzle-rush layouts are structurally broken at every viewport because of a selector mismatch. The board renders, but the panels overlap.
- **F-002**: `/history` has genuine horizontal overflow on mobile, hidden behind `overflow-x: hidden`.

## 4. Findings

### HIGH - Hard Gate violations

#### F-001 - Puzzle and Puzzle Rush grids never apply

- **Priority:** HIGH
- **Route:** `/puzzles`, `/puzzle-rush`
- **Files:** `src/pages/PuzzlePage.css:3`, `src/pages/PuzzleRushPage.css:3`, `src/pages/PuzzlePage.js:337`, `src/pages/PuzzleRushPage.js:432`
- **Rule:** R-03 (mobile), C-4 (resilience)

**Evidence.** The stylesheet scopes the layout as a descendant selector:

```css
.puzzle-mode .App-body { grid-template-columns: 260px 1fr 220px; }
```

The element is `<main className="App-body puzzle-mode">`, so the class sits on the grid container itself, not on an ancestor. Measured on the live DOM:

```
elClass: "App-body puzzle-mode"
matchesPuzzleMode: false
gridAreas: "evaluation chessboard controls" / "opening movehistory movehistory"
```

`.App-body` also declares its own `grid-template-areas`, so the panels name areas (`info`, `solution`) that do not exist in the applied template. Both are auto-placed into one cell and overlap exactly:

```
.puzzle-info-panel   { x:1023, y:576, w:361, h:365 }
.puzzle-moves-panel  { x:1023, y:576, w:361, h:167 }
```

At 360px the board collapses to **2x2 px** and the same overlap occurs. `PuzzleRushPage` has the identical defect.

**Why this is problematic.** Two panels occupy one grid cell, so one is painted over the other, and the board is the element that loses the space. This is not a spacing preference: the layout is not applying at all.

**Recommended correction.** Target the element that carries the class: `.App-body.puzzle-mode` and `.App-body.puzzle-rush-mode`. Confirm at 360, 768, and 1440px that the three panels occupy three distinct cells.

**Functional regression risk.** Low. The change enables CSS that is already written. Board rendering, move validation, and puzzle logic are untouched. The risk sits in the `max-width: 1100px` single-column fallback, which must keep the stack order `board, info, solution`.

**Expected improvement.** On both puzzle routes the board regains its column and the two panels stop covering each other, so the primary task becomes readable at every breakpoint.

#### F-002 - Horizontal overflow on /history and /online, masked by overflow-x: hidden

- **Priority:** HIGH
- **Route:** `/history`, `/online`
- **Files:** `src/pages/HistoryPage.css:7`, `src/App.css:17-26`, `src/OnlineLobby.css:41-47`, `src/index.css:16`
- **Rule:** R-03 (mobile)

**Evidence.** Measured at 360px:

```
/history  documentElement.scrollWidth - clientWidth = 22px
          .history-page  right: 378  (viewport 356)
/history  .history-header right: 361, .gh-panel right: 361

/online   .online-lobby-card right: 380, width: 380  (viewport 356)
```

No global `box-sizing: border-box` reset exists. `src/design-system.css:72` applies it to `.App-header` only, so width-plus-padding adds up on every other element. `.App` is a flex container with `align-items: center`, and `.history-page` declares `width: 100%` plus `padding: 32px 24px` with no `border-box`, so it is 48px wider than its track.

The overflow is invisible in use because `body` sets `overflow-x: hidden` (`src/index.css:16`), which clips the content instead of scrolling it. The symptom the user sees is not a scrollbar; it is content cut off at the right edge.

**Why this is problematic.** R-03 forbids horizontal overflow. Here the overflow is worse than usual because it is suppressed rather than surfaced: a layout that is genuinely too wide is presented as if it fits, and anything that lands in the clipped strip is unreachable. The lobby card is the clearest case, at 380px in a 356px viewport.

**Recommended correction.** Add a global `*, *::before, *::after { box-sizing: border-box; }` reset. Then remove `overflow-x: hidden` from `body` so that any remaining overflow is visible during development, and fix what it reveals. For `.online-lobby-card`, the `width: 90%` plus `padding: 32px` needs the border-box reset, or `width: min(90%, 100%)` with `padding` reduced below 480px.

**Functional regression risk.** Medium. A global border-box reset changes the computed size of every element in the app and will shift layout in places that currently compensate for the missing reset. It must be applied together with a full visual pass at all five breakpoints, and it should land as its own isolated change so any regression is attributable.

**Expected improvement.** Nothing is clipped at the right edge on mobile, `/history` and `/online` fit their viewport, and future overflow becomes detectable instead of silently hidden.

#### F-003 - Two competing token sets, and hardcoded hex values that bypass both

- **Priority:** HIGH
- **Route:** all
- **Files:** `src/index.css:28-62`, `src/design-system.css:6-48`, `src/index.js:3,6`
- **Rule:** R-29 (palette), R-31 (reasons written)

**Evidence.** Two complete `:root` blocks define the same custom properties with different values:

`src/index.css:28`
```css
--bg-primary: #F0F2F5;
--accent-primary: #2563EB;   /* Bright Blue */
--online-accent: #059669;    /* Emerald 600 */
--board-light: #D1D5DB;
```

`src/design-system.css:6`
```css
--bg-primary: #e8ece9;
--accent-primary: #914326;   /* copper */
--online-accent: #4e7867;    /* sage */
--board-light: #e8d8bd;
```

`src/index.js` imports `./index.css` on line 3 and `./design-system.css` on line 6, so the design-system values win. The older blue set is dead weight that still misleads anyone reading `index.css` first.

The bigger problem is that page stylesheets do not use either token set consistently. Live computed values for the primary button:

```
backgroundImage: linear-gradient(135deg, rgb(37,99,235), rgb(5,150,105))
color: rgb(22,27,25)
borderColor: rgb(201,102,67)
```

That is the `index.css` blue, the `index.css` emerald, and the `design-system.css` copper border, in one component. Off-palette hardcodes also appear in `LandingScreen.css:700` (`#a78bfa`), `:705` (`#f59e0b`), `:710` (`#8b5cf6`), and in gradient stacks at `LandingScreen.css:582`, `pages/PuzzlePage.css:284`, `pages/PuzzleRushPage.css:382`, `pages/HistoryPage.css:84`.

**Why this is problematic.** R-29 caps the active palette at 2 to 3 core colors plus one accent. The live app uses copper, sage, blue, emerald, violet, and amber. R-31 requires a one-line reason for each decision; no reason exists for running two token systems, and none exists for the violet and amber additions. When tokens and hardcodes disagree, theming silently stops working for the hardcoded parts, which is exactly what F-006 and F-007 show.

**Recommended correction.** Collapse to one token set: keep `design-system.css` as the single source, delete the duplicate `:root` in `index.css` (keeping only the Inter import decision, see F-013), and replace every hardcoded hex in the page stylesheets with the corresponding token. Any hue that has no token gets either a new semantic token with a written reason or is removed.

**Functional regression risk.** Medium. Removing the second `:root` is safe because it currently loses the cascade, but replacing hardcoded hex will visibly change several gradients and badges. It must be done with the palette decision from section 8 settled first, and verified in both themes.

**Expected improvement.** One palette, one place to change it, and a theme toggle that reliably reaches every surface. Six competing hues reduce to a deliberate three plus one accent.

#### F-006 - Primary button fails WCAG AA in dark mode

- **Priority:** HIGH
- **Route:** all routes that render a primary action
- **Files:** `src/App.css:406-415`, `src/design-system.css:197-205`
- **Rule:** R-25 (contrast), R-34 (themes)

**Evidence.** `App.css:407` sets a gradient background and `App.css:409` sets white text; `App.css:414` then replaces the dark-theme gradient with a hardcoded blue-to-emerald pair while leaving the text colour as inherited near-black:

```css
.button-primary {
  background: linear-gradient(135deg, var(--accent-primary), var(--online-accent));
  color: #fff;
}
[data-theme='dark'] .button-primary {
  background: linear-gradient(135deg, #2563EB, #059669);
}
```

Measured contrast in dark mode:

```
near-black text #161b19 on blue stop    #2563EB = 3.37:1   FAIL (needs 4.5)
near-black text #161b19 on emerald stop #059669 = 4.63:1   pass
white text      #ffffff on emerald stop #059669 = 3.77:1   FAIL
white text      #ffffff on blue stop    #2563EB = 5.17:1   pass
```

The rendered text colour is `rgb(22,27,25)`, near-black, because `design-system.css:201` sets `color: var(--accent-on-fill)`, which is `#161b19` in dark theme and overrides the `#fff` from `App.css:409` on specificity and order. The border is copper, a third hue.

Neither text colour clears both gradient stops. The button fails at the blue end with dark text and would fail at the emerald end with white text, so the gradient itself is the defect, not the text colour choice.

**Why this is problematic.** This is the most-clicked control in the app, it fails the Hard Gate on contrast, and it does so in only one of the two themes, which is precisely the R-34 failure mode. A gradient that cannot carry a single accessible text colour is a gradient that should not be behind text.

**Recommended correction.** Use the token pair that already works: `background: var(--accent-primary)` with `color: var(--accent-on-fill)`. Measured, that is white on copper at 6.92:1 in light and near-black on copper at 4.54:1 in dark, both passing. Remove the `[data-theme='dark']` gradient override and the `#fff` override entirely.

**Functional regression risk.** Low. The change is limited to background and text colour on one button class. It touches every primary action visually, so the six routes must be checked for any place that relied on the gradient to stand out.

**Expected improvement.** The primary action passes AA in both themes, the button stops carrying three conflicting hues, and the accent token becomes the single source of truth for it.

#### F-007 - All six landing badges fail contrast and use four off-palette hues

- **Priority:** HIGH
- **Route:** `/`
- **Files:** `src/LandingScreen.css:675-712`, `src/LandingScreen.js:543,553,563,573,583,592`
- **Rule:** R-25 (contrast), R-09 (badges), R-29 (palette)

**Evidence.** Each mode card carries a capsule badge whose colour is set per variant. Measured in dark theme, with white text on each badge background:

```
"Popular"  bg #c96643 (copper)  = 3.84:1  FAIL
"1v1"      bg #78a992 (sage)    = 2.66:1  FAIL
"Live"     bg #a78bfa (violet)  = 2.72:1  FAIL
"Free"     bg #f59e0b (amber)   = 2.15:1  FAIL
"Timed"    bg #c96643 (copper)  = 3.84:1  FAIL
"Review"   bg #8b5cf6 (violet)  = 4.23:1  FAIL
```

Every badge is `font-size: 8.8px`, `text-transform: uppercase`, `border-radius: 999px`, `padding: 3.2px 8.8px`. That is six of six failing, at a text size where legibility is already marginal.

**Why this is problematic.** Three rules fail at once. R-25 is a Hard Gate and all six fail it. R-09 forbids capsule badges without a functional need, and these six duplicate the card title directly below them ("Popular" above "Analysis Mode", "Live" above "Watch Live"). R-29 is breached by the violet and amber, neither of which is a token. The combination of pill, uppercase, tiny size, and four hues is the exact pattern R-09 names.

**Recommended correction.** Remove the badges. The card title already states the mode and the description already states the offer, so the badge adds a line of reading without adding a fact. If a status badge is genuinely needed for a real state (for example a live game count on "Watch Live"), keep one badge, give it a token background with a passing contrast pair, and drop the uppercase and 999px radius.

**Functional regression risk.** Very low. The badges are decorative `<span>` elements with no handler and no `aria` contract. Removing them cannot break navigation, which is driven by the parent `<button>`.

**Expected improvement.** Six contrast failures disappear, the landing page drops from six hues to the intended three plus accent, and each card is read in one step instead of two.

#### F-008 - Sixteen infinite loops on the landing page contradict MOTION 1

- **Priority:** HIGH
- **Route:** `/`
- **Files:** `src/LandingScreen.css:322-467`, `src/index.css:220-260,413,483,516-566`
- **Rule:** R-19 (animation), R-13 (glow), Block 3 liveliness

**Evidence.** `LandingScreen.css:322` and `:336` create two 600-700px radial orbs that float forever:

```css
.landing-screen::before {
  background: radial-gradient(circle, rgba(52,152,219,0.10) 0%, ...);
  animation: orb-float-1 20s ease-in-out infinite;
}
.landing-screen::after {
  background: radial-gradient(circle, rgba(16,185,129,0.08) 0%, ...);
  animation: orb-float-2 25s ease-in-out infinite;
}
```

`LandingScreen.css:398-455` adds six `floating-piece` elements, each `animation: float-piece-N ... infinite` with a staggered delay. `index.css` adds 24 more infinite declarations, including `cp-glow-pulse`, six `cp-*-idle` piece bob loops, `ps-dot-glow`, `board-shimmer-drift`, and twelve `bp-*-float` loops. Live count on `/`: 6 `.floating-piece` elements, 16 infinite animations in `LandingScreen.css` alone, 56 across the codebase.

`DESIGN.md` declares **MOTION 1**, and `design-system.css:687` even states "Decorative infinite motion is disabled."

**Why this is problematic.** R-19 requires motion to serve a stated purpose and to match the declared dial. At MOTION 1 the contract is hover states only; sixteen endless loops is the opposite. The orbs and floating pieces also fail R-13 and R-01: they are decorative colour fields in blue and emerald that are not in the palette, behind content, doing no hierarchy work. Reduced motion is handled correctly (see the PASS note), so the issue is the default state, not the fallback.

**Recommended correction.** Remove the two orbs and the six floating pieces. Keep one motion moment if the landing needs an entrance, such as the existing card stagger, and stop it after it plays. The grid overlay in F-005 should go with them. The identity should come from typography and the scoresheet motif, which already exist and are stronger.

**Functional regression risk.** Low. All affected elements are `aria-hidden="true"` decorations with `pointer-events: none`. Removing them cannot affect layout flow or interaction, though the landing header may need spacing re-checked once the orbs are gone.

**Expected improvement.** The landing page stops competing with its own content, the declared MOTION 1 becomes true, and two off-palette colour fields disappear from behind the type.

#### F-014 - Landing statistics mix real values with invented ones

- **Priority:** HIGH
- **Route:** `/`
- **Files:** `src/LandingScreen.js:598-627`, `src/data/puzzles.js`
- **Rule:** R-17 (data & numbers), R-38 (real content), C-5 (evidence)

**Evidence.** The landing page renders four animated counters:

```jsx
<AnimatedCounter end={20} suffix=""  label="Curated Puzzles" />
<AnimatedCounter end={18} suffix=""  label="Stockfish Engine" />
<AnimatedCounter end={1}  suffix="v1" label="Online Multiplayer" />
<AnimatedCounter end={22} suffix="+"  label="Analysis Depth" />
```

Checked against the codebase:

- **"Curated Puzzles" = 20** is false. `src/data/puzzles.js` contains **19** puzzle entries. The landing page also claims "20 curated puzzles" in the feature description at `:641`.
- **"Stockfish Engine" = 18** is presented as a metric but is a version number, not a quantity. `public/stockfish/` contains `stockfish-18-lite-single`, so the version is real; the framing as a statistic is not.
- **"Online Multiplayer" = 1v1** is a format, not a number.
- **"Analysis Depth" = 22+** is false. `src/pages/AnalysisPage.js:68` sets `useState(20)` as the default depth, and the landing feature card at `:536` claims "at depth 22+". The engine can reach 22 if the user raises the slider, so the claim is not impossible, but the default and the stated baseline disagree.

**Why this is problematic.** R-17 forbids numbers without a real source and R-38 forbids fabricated content that looks realistic. This is the worst version of that failure because three of the four figures are real values wearing the costume of statistics: a version number, a player count, and a depth setting are arranged in a row to look like platform metrics. The one figure that is a genuine count is wrong by one.

**Recommended correction.** Either remove the stat row entirely, since the mode cards already communicate what the app does, or replace it with figures that are computed from the source of truth at render time: `puzzles.length` for the puzzle count, and no figure at all for the others. Anything that cannot be computed should not be displayed as a number.

**Functional regression risk.** Very low. The row is presentational. Removing it changes vertical rhythm on the landing page, which F-019 already calls out for rework.

**Expected improvement.** The landing page stops making a false claim about its own content, and the credibility of the real figures (which do exist) is no longer diluted by three that are not figures at all.

#### F-009 - Em dashes in user-visible copy

- **Priority:** HIGH
- **Route:** `/puzzles`, `/online`, and every page whose `<meta>` is read
- **Files:** `src/data/puzzles.js:21-196` (19 occurrences), `public/index.html:11,15,20`, `src/hooks/useOnlineGame.js:393`
- **Rule:** R-02 (copywriting)

**Evidence.** Every puzzle description uses an em dash as a clause separator:

```js
description: 'White to play — exploit the loose knight on c6.',
description: 'Black to play — a classic fork on f2.',
description: 'White to play — a queen sacrifice to force checkmate.',
```

19 occurrences in `src/data/puzzles.js`, rendered directly in the puzzle info panel at `PuzzlePage.js:371`. Three more appear in `public/index.html` in the meta description and Open Graph and Twitter titles, which are the strings shown when the site is shared. One appears in a user-facing error message: `'Could not reserve a game slot. The server may be busy — please try again.'`

The remaining 45 matches are code comments, which are outside R-02's UI-text scope.

**Why this is problematic.** R-02 is an absolute Hard Gate with no purpose exemption. The character is the single most reliable marker of generated prose, and here it appears 23 times in strings a user actually reads, including the copy shown when the link is shared on social platforms.

**Recommended correction.** Replace each with a colon, comma, or full stop. For the puzzle descriptions the natural rewrite is `'White to play. Exploit the loose knight on c6.'` or `'White to play: exploit the loose knight on c6.'` For the meta strings, `ChessWeb: Play, analyze, and spectate chess games with Stockfish 18`. For the error, `'Could not reserve a game slot. The server may be busy, please try again.'`

**Functional regression risk.** Very low, with one caveat. Any test that asserts on a puzzle description string will fail and must be updated rather than deleted. `src/lib/validation.js` and the puzzle data contract do not depend on the separator character.

**Functional regression risk.** Low. Single class, visual only.

**Expected improvement.** One accent colour on the primary action instead of three.

#### F-025 - Two gradient stops in dark mode produce an unreadable midpoint

- **Priority:** LOW
- **Route:** all
- **Files:** `src/App.css:414`
- **Rule:** R-01 (gradients), R-25 (contrast)

**Evidence.** The dark-theme override replaces a same-family gradient with two hues at very different luminance:

```css
[data-theme='dark'] .button-primary {
  background: linear-gradient(135deg, #2563EB, #059669);
}
```

Measured luminance of the two stops differs enough that no single text colour serves both: near-black reaches 3.37:1 on the blue end and 4.63:1 on the emerald end. Text sits over the whole gradient, so it passes at one edge and fails at the other. This is the exact case R-25 names when it forbids text over "a gradient that is light in some areas".

**Why this is problematic.** Even after F-006 fixes the text colour, a gradient whose stops span this much luminance cannot be made accessible with one foreground colour. The defect is structural, not a matter of picking a better text value.

**Recommended correction.** Remove the two-hue gradient. A single accent fill, or a gradient between two stops of similar luminance in the same hue, both work. F-006's recommendation covers this.

**Functional regression risk.** Low, and overlapping with F-006. If both are approved they should be implemented together as one change.

**Expected improvement.** Text over the primary action has consistent contrast across its full width.

#### F-026 - Emoji used as empty-state icons and as a streak badge

- **Priority:** LOW
- **Route:** `/history`, `/puzzles`, `/puzzle-rush`
- **Files:** `src/components/GameHistoryPanel.js:99,111`, `src/pages/PuzzlePage.js:400`, `src/pages/PuzzleRushPage.js:614`
- **Rule:** R-04 (icons)

**Evidence.** Four user-visible emoji carry meaning that an icon or a word should carry:

```jsx
<div className="gh-empty-icon" aria-hidden="true">⚠️</div>   // error state
<div className="gh-empty-icon" aria-hidden="true">📜</div>   // empty state
<span className="solved-icon">🎉</span>                      // puzzle solved
<span className="rush-streak-badge">{streak} streak 🔥</span> // rush streak
```

Note the inconsistency: the two history states are `aria-hidden`, so assistive technology gets the text only, while the solved and streak emoji are announced.

**Why this is problematic.** The antislop-ui skill names emoji as decoration that flattens product voice and competes with content. Here they are also the only visual marker for two distinct history states, which means the difference between "empty" and "unavailable" is carried by a warning sign and a scroll rather than by the heading, which does state it in text. The mixed `aria-hidden` treatment is an accessibility inconsistency rather than a deliberate choice.

**Recommended correction.** Replace with icons from the set already in use (`react-feather`), or drop the mark and let the heading carry the state. For the streak badge, the number and the word "streak" already communicate it, so the flame is removable.

**Functional regression risk.** None. All four are presentational.

**Expected improvement.** Consistent icon language across states, no emoji in the interface, and the two history states distinguished by their headings rather than by two emoji.

#### F-028 - `theme-color` meta uses a colour that is not in the palette

- **Priority:** LOW
- **Route:** all
- **Files:** `public/index.html:7`
- **Rule:** R-29 (palette), R-31 (reasons written)

**Evidence.**

```html
<meta name="theme-color" content="#3498DB" media="(prefers-color-scheme: light)" />
<meta name="theme-color" content="#18191A" media="(prefers-color-scheme: dark)" />
```

`#3498DB` is the old bright blue from the first palette generation. It matches neither `--accent-primary` (`#914326` copper) nor any current token. The dark value `#18191A` is also the old `index.css` background, not the current `#121817`.

**Why this is problematic.** `theme-color` paints the browser chrome on Android and the status bar area in some contexts, so it is a visible surface. It is currently the only remaining place where the abandoned blue palette reaches the user, and it is the first colour a mobile user sees before the app renders.

**Recommended correction.** Point both values at the current tokens: copper or the ivory background for light, `#121817` for dark. Since the values must be literal in HTML, add a comment naming the token each one mirrors so the next palette change does not miss them again.

**Functional regression risk.** None.

**Expected improvement.** The browser chrome matches the app on mobile, and the last trace of the retired palette is gone.

#### F-029 - The chessboard grid pattern is rendered twice

- **Priority:** LOW
- **Route:** `/`
- **Files:** `src/LandingScreen.js:505,513`
- **Rule:** C-1 (intentionality)

**Evidence.** The same `bg-pattern` element appears in both trees:

```jsx
505:  <div className="bg-pattern" aria-hidden="true" />   // skeleton overlay
513:  <div className="bg-pattern" aria-hidden="true" />   // real content
```

Because `.bg-pattern` is `position: fixed; inset: 0`, both instances occupy the same viewport area. They coexist during the crossfade.

**Why this is problematic.** Fixed positioning plus two instances means the pattern is composited twice during the transition, at double the intended opacity, which is visible as a brief darkening on the landing page. It is a small visual artefact, but it indicates the skeleton and real trees were built independently rather than as one.

**Recommended correction.** This disappears if F-020 is approved, since the skeleton is removed. If the skeleton stays, render the pattern once at a level above both trees.

**Functional regression risk.** None.

**Expected improvement.** No double-darkening during the landing transition.

#### F-030 - "20 curated puzzles" stated twice, and the count is 19

- **Priority:** LOW
- **Route:** `/`
- **Files:** `src/LandingScreen.js:601,641`, `src/data/puzzles.js`
- **Rule:** R-17 (data), R-31 (reasons written)

**Evidence.** The figure appears as a stat (`end={20}`, label "Curated Puzzles") and again in the feature copy at `:641`: "Sharpen your pattern recognition with 20 curated puzzles." `src/data/puzzles.js` defines 19 entries.

**Why this is problematic.** Two independent hardcoded copies of one number, both wrong, and neither derived from the data they describe. Even if the count were right today, adding a puzzle would silently make both wrong again.

**Recommended correction.** If the figure is kept, derive it: `import { puzzles } from './data/puzzles'` and render `puzzles.length`. Otherwise remove both mentions. This is the same root cause as F-014, recorded separately because the fix is a data binding rather than a deletion.

**Functional regression risk.** None.

**Expected improvement.** The stated count cannot drift from the actual count.

#### F-031 - The header renders "CHESSWEB" from CSS `content`

- **Priority:** LOW
- **Route:** all except `/`
- **Files:** `src/design-system.css:80-86`
- **Rule:** R-39 (semantics), C-1 (intentionality)

**Evidence.**

```css
.App-header-nav::before {
  content: "CHESSWEB";
  font-size: 0.72rem;
  font-weight: 800;
  letter-spacing: 0.18em;
}
```

The wordmark is injected as generated content rather than markup. CSS `content` text is inconsistently exposed to assistive technology and cannot be selected, translated by page-level translation tools, or found by in-page search.

**Why this is problematic.** R-39 requires content to be perceivable. A brand name is content. Rendering it through `::before` also means the header has no accessible brand element, which matters because it is the only identifying element on every route and it is not a link home, while the "Back to Home" button next to it does that job.

**Recommended correction.** Render the wordmark as real text in `AppLayout.js`, inside a `<Link to="/">` so it doubles as a home affordance, and remove the `::before` rule. The letter-spaced small-caps treatment can stay as styling on the real element.

**Functional regression risk.** Low. The visual result is identical if the typography is carried over. Making it a link changes one interaction, and the existing "Back to Home" button already covers that path, so the two should be reconciled rather than duplicated.

**Expected improvement.** The wordmark becomes selectable, searchable, translatable, and available to assistive technology, and it gains the home-link behaviour users expect from a header logo.

## 5. Route-by-route assessment

Each route is judged against the primary task the user comes to it for.

### `/` Landing

**Does it work?** Yes. Purpose is clear within one screen, all six modes are reachable, and the primary task (choose a mode) is a single click.

**What is strong.** The mode card grid is genuinely good information architecture: six routes, six cards, keyboard shortcuts 1 to 5 printed on the cards, and a real destination behind each. That is better than most landing pages, because it is a menu rather than a pitch. The tagline names the engine and the three activities immediately.

**What is weak.** The page is doing three jobs and only needs one. A menu, a stats panel, and a features showcase are stacked, and the last two repeat the first (F-014, F-018). Six badges, sixteen infinite animations, two radial orbs, and a tiled grid overlay all compete with the six cards that actually matter (F-007, F-008, F-005). A fabricated progress bar withholds the page for up to 900ms before any of it is visible (F-020).

**Focal point.** Present but contested. The mode cards should be the single focal point; the stat row and the feature grid both argue for equal attention.

### `/analysis`

**Does it work?** Yes. This is the strongest route.

**What is strong.** The board is the primary element and behaves like it: 332px at 360px, 383px at 1440px, centred, with the evaluation panel and move history as supporting columns that collapse cleanly to one column on mobile. The evaluation bar, the depth control, and the move classification have real hierarchy. This is the one route where the editorial scoresheet direction is visible in the structure rather than applied as decoration.

**What is weak.** `depth 22+` is claimed on the landing page but this route defaults to 20 (F-016). Evaluation numbers and clocks do not use tabular numerals (F-012), so digits shift as values change. The primary Import button inherits the three-hue gradient (F-006, F-024).

**Focal point.** Clear: the board.

### `/online`

**Does it work?** Partially. The lobby renders and is usable, but the card overflows its viewport on mobile (F-002).

**What is strong.** Time control options are specific and complete (1, 3, 5, 10, 30 min, untimed). Create and Join are visually distinct and correctly ordered. The game actions are plain words rather than icons.

**What is weak.** The lobby card is 380px wide in a 356px viewport, so its right edge, including part of the Create Game button, is clipped (F-002). The card carries a three-hue gradient rule across its top edge (`OnlineLobby.css:61`) and stacks three backdrop blurs. The mid-game state could not be inspected in this build, so player information, clock prominence, and connection status are **unassessed**; they are recorded as unverified rather than passed.

**Focal point.** Create Game, correctly.

### `/puzzles`

**Does it work?** No, structurally. The three-column layout never applies (F-001), so the info panel and the moves panel occupy the same grid cell, and on mobile the board collapses to 2x2px.

**What is strong.** The puzzle content itself is real: 19 positions with FEN, solution, themes, and a difficulty rating. The solving interaction and feedback exist. The empty state before Start Training names the next action.

**What is weak.** Beyond the grid failure, the difficulty chips are 35px tall (F-027), the descriptions carry em dashes (F-009), and the info panel has no clear hierarchy between the rating, the ID, the themes, and the description.

**Focal point.** Intended: the board. Actual: whichever panel wins the overlap.

### `/puzzle-rush`

**Does it work?** Same structural failure as `/puzzles` (F-001): HUD and solution panels share a cell, board collapses on mobile.

**What is strong.** The HUD concept is right: progress and remaining time are the two things this mode is about, and they are placed together. Streak and lives are present.

**What is weak.** The progress and timer cannot be evaluated as readable because they are stacked into the wrong cell. The streak badge carries an emoji (F-026).

**Focal point.** Intended: the timer. Unverified in practice because of F-001.

### `/history`

**Does it work?** The error and empty states work correctly and are honest. The populated state could not be inspected in this build.

**What is strong.** This is the best-handled data surface in the app. `GameHistoryPanel` implements all three states properly (`:95` unavailable, `:107` empty, `:128` loading), each with a heading and an explanatory sentence rather than a bare spinner, and `/history` uses `useLoadingSequence({ manual: true })` so the skeleton waits for the real fetch instead of a timer. That is the correct pattern, and it is the one the landing page should have used (F-020).

**What is weak.** 22px horizontal overflow at 360px (F-002). The two states are distinguished by emoji rather than by their headings (F-026).

**Focal point.** Clear: the game list, with the states handling its absence well.

## 8. Accessibility assessment

### Passing

These were checked and genuinely hold. They deserve recording because the app does them better than most.

- **Focus visibility.** 47 `:focus-visible` rules. Every one of the 11 `outline: none` declarations is paired with a replacement: `App.css:1477` gives range inputs a ring, `Modal.css:15` gives the dialog a ring, `App.css:1494` gives the board wrapper a 3px ring. No focus trap.
- **Keyboard operation.** A skip link to `#main-content` with `tabIndex={-1}` on the target. 53 focusable elements on `/analysis`, all reachable. Cards are real `<button>` elements, so Enter and Space work natively.
- **Reduced motion.** 11 `prefers-reduced-motion: reduce` blocks. The landing block (`LandingScreen.css:1788`) disables orbs, floating pieces, card stagger, scroll reveal, and 3D tilt. `index.css:741` disables all 24 skeleton animations. This is thorough, not token.
- **Landmarks and language.** `<html lang="en">`, one `<h1>` per route, `<header>`, `<main>`, `<nav aria-label="Primary navigation">`.
- **Accessible names.** The theme toggle has both `aria-label` and `title`. Icon-only buttons are labelled. Decorative icons are `aria-hidden`.
- **Viewport.** No `user-scalable=no`, no `maximum-scale=1`.
- **Themes.** Both modes load and are complete; the toggle persists to `localStorage` and respects `prefers-color-scheme` on first visit.

### Failing

- **Contrast.** The dark primary button at 3.37:1 (F-006) and all six landing badges at 2.15 to 4.23:1 (F-007). These are the two Hard Gate failures.
- **Chessboard coordinates.** The rank and file labels measure 2.21:1 against their squares in dark theme (`--board-light: #7f7565` with `#30473f` text and the inverse). At 8px and 13px these are below any threshold. I am recording this as an observation rather than a numbered finding, because board coordinates are conventionally low-contrast decoration and the pieces themselves carry the position. If the board is to be used by low-vision players, these labels need a contrast pass.
- **Tap targets.** 35px difficulty chips and a 37px skip link (F-027).
- **Announced fiction.** A `role="progressbar"` reporting timer-driven percentages on a page with no data dependency (F-020).
- **CSS-generated content.** The wordmark is `::before` content (F-031).
- **Inconsistent emoji exposure.** Two emoji are `aria-hidden`, two are announced (F-026).

### Not verified

Keyboard traversal of the multiplayer mid-game controls, the lobby dialog focus trap, and the chessboard's keyboard move entry were **not** exercised, because those states require a Supabase connection this build does not have. `useDialogFocus` exists and is tested, but I did not observe it in a live dialog. This is recorded as unverified, not as a pass.

## 10. Proposed DESIGN.md direction

`DESIGN.md` **exists** and is already close to the direction proposed for this project. It is not a prerequisite gap. It does, however, contain three points that the build contradicts, and the document itself should be reconciled with reality before any redesign starts.

### What is already right

- Personality: intelligent, calm, precise, elegant, focused, approachable. The build matches this in tone.
- Visual language: "Editorial Chess Studio", scoresheet plus analysis workspace. The `Arial Narrow` section titles and `Georgia` notation text already express it.
- Dials: ENERGY 2 / RHYTHM 2 / MOTION 1. Sensible for a study tool.
- Non-negotiables: keep both themes, no fabricated statistics, no decorative UI without purpose.

### What needs reconciling

1. **Palette.** `DESIGN.md` says "Muted blue as primary accent" and "Sage green for chessboard-related elements". The build uses **copper** `#914326` as the accent and sage `#4e7867` on the board. Copper is a defensible editorial choice and arguably better than muted blue for the stated mood, but the document and the code currently disagree, and R-31 requires the reason to be recorded. **Decision needed:** amend `DESIGN.md` to name copper, or change the code to muted blue.
2. **Typography.** `DESIGN.md` names Open Sans. Nothing in the build uses it. **Decision needed:** name the actual stack, and decide the serif-for-headings question, since `Georgia` is already in use and supports the editorial voice.
3. **Tabular numerals.** Required by the document, absent from the code. This one needs no decision, only implementation.

### Proposed amendments, for review

```
## Color Direction (revised)

Light theme:
- Warm ivory backgrounds (--bg-primary #e8ece9, --bg-secondary #f7f8f5)
- Deep charcoal typography (--text-primary #17211e)
- Copper as the single primary accent (--accent-primary #914326)
  Reason: copper reads as ink and brass rather than as a software brand
  colour, which supports the scoresheet direction. It replaces the earlier
  muted-blue proposal.
- Sage for board-adjacent state (--online-accent #4e7867)

Dark theme:
- Deep slate backgrounds (#121817 / #1b2421)
- Soft off-white typography (#e7eeea)
- Copper lifted for dark contrast (#c96643)

Removed: violet (#a78bfa, #8b5cf6) and amber (#f59e0b). Neither carries
meaning the copper and sage pair does not already carry.

## Typography (revised)

UI sans: Segoe UI Variable, falling back to Avenir Next, Segoe UI, sans-serif.
  Reason: system stack, zero network cost, already rendering.
Editorial headings: Arial Narrow, uppercase, 0.08em tracking.
  Reason: scoresheet column headers.
Notation and codes: Courier New, monospace, tabular-nums.
  Reason: fixed-width alignment for move lists and invite codes.

No webfont is loaded. The Inter import is removed.
```

The palette proposal keeps the project's own direction and drops two hues that no rule required. It is a smaller change than it looks: copper and sage are already the tokens, so most of the work is deleting violet and amber rather than inventing anything.
